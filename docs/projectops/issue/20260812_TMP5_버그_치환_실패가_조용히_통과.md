### 무슨 일이 있었나요?

**치환값을 구하지 못하면 마법사가 아무 말 없이 넘어가고, 플레이스홀더가 그대로 남은 워크플로우가 설치됩니다.**

`src/core/wizard-env.js` 의 `setEnvLine` 은 값이 빈 문자열이면 그 줄을 원본 그대로 돌려줍니다. 원래는 "사용자가 답을 안 했으면 템플릿 기본값을 유지한다"는 의도지만, `@wizard auto:` 토큰처럼 **마법사가 스스로 계산해야 하는 값**에서는 의미가 정반대가 됩니다. 계산에 실패해도 실패했다는 사실이 어디에도 드러나지 않습니다.

실제로 터진 사례가 있습니다. Spring 배포 워크플로우 4개는 `APPLICATION_YML_DIR` 값을 `@wizard auto:spring-app-yml-dir` 로 자동 계산합니다. 이 계산은 `src/core/detect-fs.js` 의 `findSpringAppYml` 이 담당하는데, 파일명 판정이 `/^application.*\.yml$/` 라서 **`application.yaml`(YAML 공식 확장자, Spring 공식 지원)을 찾지 못합니다.**

```
application.yml    → 매칭됨
application.yaml   → 매칭 안 됨
```

그 결과 이런 일이 벌어집니다.

1. `findSpringAppYml` 이 빈 문자열 반환
2. `setEnvLine` 이 빈 값이므로 그 줄을 건드리지 않음
3. 설치된 워크플로우에 `APPLICATION_YML_DIR: "__APPLICATION_YML_DIR__"` 가 그대로 남음
4. **설치는 성공으로 끝남. 경고 한 줄 없음**
5. 배포 시 워크플로우가 `__APPLICATION_YML_DIR__` 라는 이름의 디렉토리를 만들고 거기에 `application-prod.yml` 을 씀
6. 그 파일은 jar 안에 들어가지 않음 → prod 설정 없이 기동 → DB 접속 실패

**문제의 핵심은 3번과 4번 사이입니다.** `.yaml` 미지원은 고치면 되는 개별 버그지만, "치환에 실패해도 설치가 성공으로 끝난다"는 구조가 남아 있으면 앞으로 추가되는 모든 `auto:` 토큰이 같은 방식으로 조용히 실패할 수 있습니다.

같은 구조의 위험이 `spring-app-yml-path`, `flutter-root` 에도 있습니다. 이들 역시 resolver 가 빈 값을 돌려줄 수 있고, 그때 아무 경고가 없습니다.

### 기대했던 동작

- `application.yaml` 도 `application.yml` 과 동등하게 인식되어야 합니다. Spring 은 두 확장자를 모두 공식 지원합니다.
- `@wizard auto:` 토큰 계산이 실패하면 **설치 중에 사용자에게 보여야 합니다.** 어떤 파일의 어떤 키를 못 채웠는지, 그래서 무엇을 직접 고쳐야 하는지가 나와야 합니다.
- 설치 마지막에 **설치된 워크플로우에 미치환 플레이스홀더(`__..__`)가 남아 있는지 검증**하고, 남아 있으면 완료 화면에 경고로 보여줘야 합니다. 지금은 설치가 "성공" 이라고 말하는데 실제로는 동작하지 않는 파일이 깔려 있습니다.
- 사용자가 의도적으로 비운 값(템플릿 기본값 유지)과 마법사가 계산에 실패한 값은 구분되어야 합니다. 전자는 정상, 후자는 경고 대상입니다.
