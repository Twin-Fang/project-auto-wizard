### 어떤 문제를 해결하고 싶으신가요?

**설치가 끝나면 "무엇을 어떤 값으로 설치했는지" 를 알 방법이 사라집니다.**

마법사는 설치 과정에서 꽤 많은 결정을 내리고 받아냅니다. 감지한 타입과 그 근거, 버전, 브랜치 구성, 선택 워크플로우 포함 여부, 경로 확정 결과, 그리고 환경설정 7개 항목의 답변까지. 그런데 설치가 끝나면 이 정보 대부분이 **터미널 스크롤백에만 남습니다.**

`version.yml` 에 남는 것은 버전, 타입, 경로, 브랜치, 옵션 세 개뿐입니다. 나머지, 특히 **환경설정 답변(서비스 식별자, 도메인, JDK, 볼륨 경로, SSH 인증 방식, 마운트 경로, 포트)은 워크플로우 YAML 안에 치환되어 흩어질 뿐 한 곳에 기록되지 않습니다.**

그래서 나중에 이런 상황에서 막힙니다.

- 배포가 실패했을 때 "설치할 때 포트를 뭘로 답했더라"를 알려면 워크플로우 YAML 여러 개를 열어 역추적해야 합니다.
- 워크플로우가 왜 이 조합으로 깔렸는지(Nexus 제외, Secret 백업 포함 등) 근거가 남지 않습니다.
- **AI 에이전트가 이 레포에서 작업할 때 참고할 근거가 없습니다.** 에이전트는 스크롤백을 볼 수 없습니다. 지금은 설치 이력을 물어보면 워크플로우 파일을 역으로 읽어 추측하는 수밖에 없습니다.
- 재설치나 업데이트 후 "이전 설치와 뭐가 달라졌는지" 비교할 기준점이 없습니다.

디버깅과 인수인계는 결국 "그때 무슨 일이 있었나" 를 복원하는 작업인데, 지금은 복원할 재료 자체가 남지 않습니다.

### 제안하는 해결 방법

**설치가 성공적으로 끝나면 `.github/.wizard/logs/` 아래에 설치 로그 파일을 한 개 남깁니다.**

**위치를 `.github/.wizard/` 아래로 두는 이유** — 마법사는 이미 이 폴더를 자기 메타데이터 폴더로 쓰고 있습니다. 업데이트 3-way 판정에 쓰는 `baseline.json` 이 `.github/.wizard/baseline.json` 에 저장됩니다(`src/core/baseline.js`). 로그도 같은 성격의 "마법사가 소유하는 설치 메타데이터" 이므로 새 최상위 폴더를 만들 이유가 없습니다. 삭제 모드에서도 이 폴더 하나만 보면 되므로 경계가 분명해집니다.

**파일명** — 실행 시각을 파일명에 넣어 실행마다 파일이 하나씩 쌓이게 합니다. 정렬하면 그대로 시간순 이력이 되도록 정렬 가능한 형식을 씁니다. (예: `20260812-181530-install.md`) 동작 종류(설치 / 업데이트 / 삭제)도 파일명에서 구분되면 좋습니다.

**형식** — 사람도 읽고 에이전트도 파싱할 수 있어야 합니다. 상단에 기계가 읽기 쉬운 메타 블록(YAML front matter)을 두고, 아래에 사람이 읽는 마크다운 본문을 두는 구조를 제안합니다.

**남길 내용**

- **실행 정보**: 실행 시각, 마법사 버전, 템플릿 버전, 설치 모드, 신규 설치인지 업데이트인지(업데이트면 이전 템플릿 버전)
- **감지 결과와 그 근거**: 감지된 타입과 각 타입을 그렇게 판단한 마커 파일, 감지된 버전과 그 출처 파일(폴백이면 폴백이라는 사실), 브랜치
- **사용자가 답한 모든 질문과 답**: 질문 문구와 답, 그리고 그 답이 **기본값 그대로인지 직접 입력한 값인지** 구분. 나중에 "이건 내가 정한 값인가 그냥 기본값인가" 가 디버깅에서 제일 자주 필요합니다.
- **환경설정 답변 전체**: 항목 키, 최종 값, 그 값이 어느 워크플로우에 쓰였는지
- **설치 결과**: 새로 추가된 파일, 갱신된 파일, 건너뛴 파일과 그 이유(충돌 3지선에서 무엇을 골랐는지), 되살리지 않기로 한 삭제 파일
- **남은 할 일**: 설치된 워크플로우가 요구하는 GitHub Secret 목록과 권한 설정 등, 완료 화면에 안내되는 후속 조치

**민감 정보 정책** — 현재 질문 항목에는 비밀값이 없지만(도메인, 경로, 포트, 인증 *방식*), 앞으로 비밀값 항목이 추가될 수 있습니다. 값을 그대로 적지 않고 마스킹할 항목을 지정할 수 있는 규칙을 처음부터 두는 편이 안전합니다. 이 파일은 레포에 커밋되는 것을 전제로 하므로 더욱 그렇습니다.

**커밋 대상** — 에이전트가 레포에서 읽을 수 있어야 목적을 달성하므로 gitignore 하지 않고 커밋합니다.

**로그 누적** — 재설치를 반복하면 파일이 계속 쌓입니다. 최근 N개만 유지하고 오래된 것을 정리하는 정책이 필요한지 함께 정해야 합니다. (개인적으로는 이력 자체가 가치이므로 자동 삭제보다 유지 쪽에 무게를 둡니다.)

**삭제(uninstall) 처리** — 완전 삭제 모드가 이 폴더를 어떻게 다룰지 정해야 합니다. 삭제 기록도 로그로 남기는 것이 일관되지만, 그러면 삭제 후에도 폴더가 남습니다. 삭제 시에는 "삭제 로그를 남기고 폴더는 유지" 와 "폴더까지 제거" 중 어느 쪽인지 명시가 필요합니다.

**로그 기록 실패는 설치를 실패시키지 않습니다.** 쓰기 권한 문제 등으로 로그를 못 남기더라도 설치 자체는 성공으로 끝나고, 경고만 출력합니다.

### 고려한 다른 방법(선택)

- **`version.yml` 에 전부 몰아넣기** — 새 파일이 안 생겨 깔끔하지만, `version.yml` 은 릴리스 워크플로우가 매 릴리스마다 고쳐 쓰는 파일입니다. 이력성 데이터를 섞으면 파일이 계속 비대해지고 자동 갱신과 충돌합니다. 무엇보다 실행마다 한 건씩 쌓이는 이력을 담기에 맞지 않는 구조입니다.
- **`.github` 밖(예: 레포 루트 `docs/`)에 남기기** — 사용자 문서 영역을 마법사가 침범하게 됩니다. 마법사가 관리하는 산출물은 `.github` 아래로 모으는 편이 삭제 모드에서도 경계가 분명합니다.
- **`.github/logs/` 처럼 도구명 없는 경로** — 짧지만 너무 일반적이라 다른 도구나 CI 산출물과 충돌할 수 있습니다. 이 폴더가 마법사 소유라는 사실이 경로에서 드러나지 않으면 삭제 모드에서 남의 파일까지 지울 위험도 생깁니다.
- **로그를 커밋하지 않고 gitignore** — 로컬 디버깅에는 충분하지만 "에이전트가 나중에 확인" 이라는 목적을 달성하지 못합니다. 다른 사람이 클론한 레포에서는 아무것도 볼 수 없습니다.
