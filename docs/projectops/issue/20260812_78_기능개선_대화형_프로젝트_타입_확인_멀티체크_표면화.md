### 어떤 문제를 해결하고 싶으신가요?

마법사는 마커 파일을 보고 프로젝트 타입을 스스로 판단합니다. 여기까지는 좋습니다. 문제는 **그 판단이 맞는지 사용자에게 물어보는 단계가 표면에 없다**는 점입니다.

실제 설치 흐름에서 타입은 이렇게 흘러갑니다.

1. `✓ build.gradle 발견 → spring 감지` 라고 통보 (질문 아님)
2. 분석 결과 카드에 `📂 타입  spring` 이라고 표시 (질문 아님)
3. `이 정보로 진행할까요?` → `예, 계속 진행` / `수정하기` / `아니오, 취소`

타입을 고치려면 3번에서 `수정하기` 를 고르고 → `어떤 항목을 수정할까요?` 에서 `프로젝트 타입` 을 고르고 → 그제서야 멀티체크 화면이 나옵니다. **멀티체크 UI는 이미 있지만 두 단계 뒤에 숨어 있습니다.**

이게 문제가 되는 이유:

- **`이 정보로 진행할까요?` 는 최종 확인처럼 읽힙니다.** 처음 쓰는 사람은 여기가 타입을 고칠 수 있는 자리라고 인지하지 못하고 그냥 `예` 를 누릅니다.
- **타입이 틀리면 설치 결과 전체가 틀립니다.** 어떤 CI/CD 워크플로우가 깔릴지, 어떤 파일이 버전 동기화 대상이 될지, 뒤에 나오는 환경설정 질문이 몇 개일지가 전부 타입에서 갈립니다. 되돌리려면 재설치해야 합니다.
- **멀티타입 프로젝트가 특히 취약합니다.** 한 레포에 Spring + React 가 같이 있어도 마커 스캔이 하나만 잡으면 나머지는 조용히 빠집니다. 사용자가 "여기에 React 도 있는데" 라고 개입할 자연스러운 자리가 없습니다.
- 반대로 과잉 감지도 있습니다. 스크립트용 `requirements.txt` 하나 때문에 python 이 딸려 들어오는 식인데, 이것도 걷어낼 자리가 없습니다.

즉 감지는 **추정**인데 지금 UI는 이걸 **결정**처럼 제시합니다. 추정은 확인받아야 합니다.

### 제안하는 해결 방법

**감지 직후에 타입 확정 단계를 하나의 독립된 질문으로 올립니다.**

- 감지 로그를 찍은 바로 다음, 다른 질문(Nexus / Secret 백업 / 자동 버전 승격)보다 **먼저** 타입 멀티체크를 띄웁니다.
- 감지된 타입은 미리 체크된 상태로, 나머지 지원 타입은 체크 해제 상태로 전부 나열합니다. 그대로 Enter 하면 감지 결과가 그대로 확정되므로, 감지가 맞는 경우 추가 부담은 Enter 한 번입니다.
- 감지된 항목에는 **왜 그렇게 판단했는지 근거 파일을 함께 표시**합니다. (예: `spring — build.gradle.kts 발견`) 근거가 보여야 사용자가 맞는지 틀린지 판단할 수 있습니다.
- 타입이 선택에 따라 무엇이 바뀌는지 한 줄로 알려줍니다. (예: 선택한 타입에 따라 설치되는 CI/CD 워크플로우와 버전 동기화 대상 파일이 달라진다는 안내)
- 확정된 타입은 이후 분석 결과 카드에 그대로 반영되고, 기존 `수정하기` 경로는 그대로 남겨둡니다(뒤에서 다시 고치는 길은 유지).

**업데이트 설치에서는 묻지 않습니다.** `version.yml` 의 `project_types` 가 이미 단일 진실이므로, 저장값이 있으면 지금처럼 재질문 없이 재사용합니다. 이 질문은 신규 설치에서만 뜹니다.

**비대화형(`--force`, TTY 없음, `--type` 명시)에서는 건너뜁니다.** CI 자동화 경로의 동작은 지금과 완전히 동일해야 합니다.

### 고려한 다른 방법(선택)

- **분석 결과 카드의 `수정하기` 문구만 눈에 띄게 고치기** — 비용은 가장 싸지만, 여전히 "확인" 이 아니라 "이의 있으면 말해라" 구조라 근본 문제(추정을 결정처럼 제시)가 남습니다.
- **감지 결과를 예/아니오로 한 번 확인** (`spring 맞나요?`) — 틀렸을 때 결국 멀티체크로 가야 하므로 질문만 한 단계 늘어납니다. 처음부터 멀티체크를 띄우는 쪽이 질문 수가 더 적습니다.
- **감지 신뢰도가 낮을 때만 질문** — 마커 하나로 확실한 경우를 건너뛸 수 있어 매력적이지만, "신뢰도" 판정 기준을 새로 만들어야 하고 오판 시 침묵한다는 원래 문제가 그대로 남습니다.
