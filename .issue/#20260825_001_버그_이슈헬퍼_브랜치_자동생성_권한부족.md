❗[버그][이슈헬퍼] ISSUE_HELPER_CREATE_BRANCH=true로 설정해도 권한 부족으로 브랜치 자동 생성이 실패함

무슨 일이 있었나요?
---

`payload/workflows/common/PROJECT-COMMON-ISSUE-HELPER.yaml`의 `ISSUE_HELPER_CREATE_BRANCH`(39번 줄, `# @wizard ask:false` 마커로 마법사 질문에 노출됨, 이슈 #94)를 `"true"`로 켜서 이슈 생성 시 브랜치 자동 생성 기능을 사용하면, `.github/scripts/issue_helper.py`의 `create_branch_if_needed()` 함수(243번 줄)가 `POST /repos/{owner}/{repo}/git/refs`(259~260번 줄)를 호출하다가 GitHub API 403(권한 부족)으로 실패합니다.

원인은 워크플로우 파일 자체의 `permissions` 블록(25~27번 줄)이 `ISSUE_HELPER_CREATE_BRANCH` 값과 무관하게 항상 `contents: read`로 고정돼 있기 때문입니다. `git/refs` 엔드포인트에 새 ref(브랜치)를 생성하려면 `contents: write` 권한이 필요한데, 현재는 마법사에서 이 옵션을 켜도(설치 시점) 그리고 설치 후 사용자가 YAML의 `ISSUE_HELPER_CREATE_BRANCH` 값만 직접 `"true"`로 수정해도, `permissions` 블록은 자동으로 따라 올라가지 않습니다. 실제로 워크플로우 파일 자체에 이를 경고하는 주석(23~24번 줄)이 있지만, 이 주석은 워크플로우 YAML을 직접 열어보지 않는 한 아무도 보지 못하고, 마법사의 대화형 질문 흐름에도 노출되지 않습니다.

기대했던 동작
---

`ISSUE_HELPER_CREATE_BRANCH`가 `true`로 설정된 설치본에서는 이슈 생성 시 브랜치가 실제로 자동 생성되어야 합니다. 즉 `permissions.contents`가 이 기능이 정상 동작하기에 충분한 권한(`write`)으로 설정되어 있어야 합니다.

실행한 명령어
---

- 로컬 CLI 명령이 아니라 GitHub Actions 런타임에서 재현되는 문제입니다.
- 재현 경로: `npx project-auto-wizard --mode full`(대화형)에서 "이슈 생성 시 브랜치 자동 생성" 질문에 예(`ISSUE_HELPER_CREATE_BRANCH: "true"`)를 선택해 설치 → 설치된 리포에서 새 GitHub 이슈를 생성(`issues: opened` 트리거) → `PROJECT-ISSUE-HELPER` 워크플로우 실행 → `git/refs` 생성 스텝이 403으로 실패.

project-auto-wizard 버전
---

v0.8.1

OS
---

🔍 원인 분석 및 수정 방향
---

- 원인 파일: `payload/workflows/common/PROJECT-COMMON-ISSUE-HELPER.yaml` (25~27번 줄 `permissions` 블록), 도그푸딩 사본 `.github/workflows/PROJECT-COMMON-ISSUE-HELPER.yaml`도 동일하게 영향받음(두 파일은 항상 함께 수정해야 하는 이 레포의 관례).
- 수정 방향(브레인스토밍 결과, 사용자 확정): `ISSUE_HELPER_CREATE_BRANCH` 값에 따라 조건부로 권한을 올리는 대신, `permissions.contents`를 값과 무관하게 항상 `write`로 고정합니다.
  - 조건부 승격 방식은 `src/core/wizard-env.js`의 `@wizard ask` 치환 엔진이 "한 줄 = 한 key"로 설계되어 있어(다른 key 값에 따라 별개 줄을 바꾸는 기능이 없음), 이 한 파일만을 위한 특수 후처리 로직을 새로 추가해야 하고, `--force` 재설치 시의 baseline "unchanged" 판정(`isUnchanged()`/가상 렌더링) 경로에도 동일 조건을 일관되게 반영해야 하는 등 부수 복잡도가 큽니다. 또한 사용자가 설치 후 YAML의 `ISSUE_HELPER_CREATE_BRANCH` 값만 직접 수동으로 바꾸는 경우(이 레포에서 흔한 패턴)는 마법사를 다시 돌리지 않는 한 여전히 커버되지 않습니다.
  - 정적으로 `contents: write`를 고정하면 이런 부수 복잡도 없이 파일 1줄(+ 도그푸딩 사본 동기화)만 수정하면 되고, 설치 시점이든 설치 후 수동 편집이든 항상 정상 동작합니다. 브랜치 자동 생성을 쓰지 않는(기본값 `false`) 설치에서도 `contents: write`가 부여되는 것은 최소권한 원칙에서 약간 벗어나지만, 이 값이 그 외의 다른 권한을 확장하지는 않습니다(이 워크플로우가 호출하는 API는 이슈 코멘트 작성·PR 조회/수정·브랜치 생성뿐이며 `issues`/`pull-requests` 스코프는 이미 명시적으로 관리됨).
  - 23~24번 줄의 이제 사실과 다른 주석("...쓰려면 contents를 write로 올려야 한다")도 함께 제거/수정이 필요합니다.
