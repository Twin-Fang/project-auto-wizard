❗[버그][CICD] 이슈 자동 종료(Closes #N) 연결이 EnterWorktree류 브랜치명(# 없음)에서 항상 실패함

무슨 일이 있었나요?
---

이슈 #102에서 추가한 "feat/release(develop→main) PR에 이슈 자동 종료(Closes #N) 연결" 기능이 실제로는 동작하지 않고 있습니다.

원인은 `.github/scripts/issue_helper.py`의 `extract_issue_number_from_branch()`가 쓰는 `_BRANCH_ISSUE_RE = re.compile(r"#(\d+)")`입니다. 이 정규식은 브랜치명에 리터럴 `#` 문자가 있어야만 이슈 번호를 추출합니다. 이 프로젝트 자체가 생성하는 브랜치명 컨벤션(`create_branch_name()`: `{YYYYMMDD}_#{이슈번호}_{제목}`)은 이 조건을 만족하지만, `EnterWorktree` 같은 도구로 만든 브랜치명(예: `worktree-issue-118-issue-helper-branch-permission`)에는 `#`이 아예 없어 매칭에 항상 실패합니다.

이 정규식은 두 지점 모두에서 공유됩니다(코드 확인 완료):
- `extract-branch-issue` 서브커맨드 — feat PR에 `Closes #N`을 삽입하는 `.github/workflows/PROJECT-COMMON-AI-PR-SUMMARY.yaml`의 "Link related issue via branch name" 스텝(93~111번째 줄)에서 호출
- `filter_release_issue_numbers()`(`.github/scripts/changelog_manager.py` 410~424번째 줄) — release PR(develop→main)에 이슈를 취합하는 `.github/workflows/PROJECT-COMMON-AUTO-CHANGELOG-CONTROL.yaml`의 "Collect issues merged into develop" 스텝(111~143번째 줄)에서 호출

실제로 재현했습니다: `python3`으로 `_BRANCH_ISSUE_RE.search()`를 최근 worktree 브랜치명 4개(`worktree-issue-118-...`, `-110-...`, `-111-...`, `-114-...`)에 직접 실행하면 전부 `None`을 반환하고, 같은 정규식을 구 컨벤션 브랜치명(`20260824_#105_...`, `20260823_#92_...`)에 실행하면 정상적으로 번호를 추출합니다.

기대했던 동작
---

브랜치명 컨벤션과 무관하게, feat PR이 develop에 머지되면 관련 이슈 번호가 release PR(develop→main) 본문에 `Closes #N`으로 취합·삽입되어야 하고, 그 release PR이 main에 자동 머지될 때 GitHub이 해당 이슈들을 실제로 닫아야 합니다.

실행한 명령어
---

- 로컬 CLI 명령이 아니라 GitHub Actions 워크플로우(release PR pipeline)에서 재현되는 문제입니다.
- 재현 경로: `EnterWorktree` 등으로 `#`이 없는 브랜치명으로 feat PR을 열어 develop에 머지 → develop→main release PR이 자동 생성/갱신됨 → `PROJECT-AUTO-CHANGELOG-CONTROL`의 "Collect issues merged into develop" 스텝이 이슈를 하나도 못 찾음 → release PR 본문에 `Closes #N`이 삽입되지 않음 → main에 머지돼도 이슈가 자동으로 안 닫힘.

🔍 원인 분석 및 수정 방향
---

- 실측 증거: `gh run view --log`로 v0.8.0 릴리스 PR(#115, 2026-08-25)과 가장 최근 릴리스 PR(#120, 2026-08-26)의 "Collect issues merged into develop" 스텝 로그를 직접 확인 — 둘 다 `이번 릴리스에 연결할 이슈 없음 — 건너뜀`을 출력했습니다. 두 릴리스 모두 실제로는 이슈 #110/#111(v0.8.0 포함), #118(최신 포함)을 포함하고 있었는데도입니다. 해당 release PR들의 최종 본문(`gh api .../pulls/N`)에도 `Closes #N`이 전혀 없음을 확인했습니다.
- 반증 사례: 구 컨벤션 브랜치(`#` 포함)로 진행된 이슈 #82/#99/#105는 각각 해당 release PR 머지 몇십 초 뒤 정상적으로 CLOSED됨(`gh api .../issues/N`으로 확인) — 브랜치명이 컨벤션을 지켰을 때는 메커니즘 자체는 정상 동작함을 확인했습니다.
- 수정 방향(후보, 브레인스토밍 필요 — 아직 결정 안 됨):
  1. `_BRANCH_ISSUE_RE`를 `#(\d+)` 대신 `(?:#|issues?/)(\d+)` 형태로 넓혀 `worktree-issue-N-...`류 브랜치명도 매칭하도록 함(간단하지만 향후 다른 네이밍 관례가 또 생기면 재발 가능).
  2. 브랜치명 대신(또는 폴백으로) PR 제목이나 커밋 메시지에서 이슈 URL 패턴(`/issues/(\d+)`)을 추출하는 방식으로 전환 — 이 프로젝트의 PR 제목 컨벤션(`/prp-pr`가 생성하는 `{브랜치명} : {type} : {설명} {이슈URL}`)과 커밋 메시지 컨벤션 둘 다 이슈 URL을 항상 포함하고 있어, 브랜치 네이밍과 무관하게 결정론적으로 100% 신뢰 가능합니다. GitHub AI/LLM으로 유추하는 방식도 검토했으나, 이미 결정론적 신호(PR 제목의 이슈 URL)가 항상 존재하므로 비결정성·API 비용·지연만 추가하는 과한 접근으로 판단해 제외했습니다.
  3. 두 방식을 병행(브랜치명 우선 시도, 실패 시 PR 제목/커밋 메시지 폴백)해 하위 호환성과 견고성을 동시에 확보하는 방법도 고려할 만합니다.
- 부수 발견: 이전 세션에서 이슈 #110이 release PR 머지 54초 뒤 CLOSED된 것을 이슈 #102 자동화의 동작으로 추정(confidence: medium)했었는데, 이번에 실제 릴리스 실행 로그에서 그 릴리스가 "이슈 없음"으로 취합된 것을 직접 확인했으므로 그 추정은 틀렸던 것으로 보입니다 — #110은 자동화가 아니라 사용자가 수동으로 닫았을 가능성이 훨씬 높습니다.
