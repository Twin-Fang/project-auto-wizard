🚀[기능개선][CICD] feat 및 release(develop→main) PR에 이슈 자동 종료(Closes #N) 연결 추가

어떤 문제를 해결하고 싶으신가요?
---

이 프로젝트는 `version.yml`의 `metadata.template.branches.mode`가 `pr-flow`로, `feat → develop → main` 흐름을 전제로 합니다(`.github/workflows/PROJECT-COMMON-AUTO-CHANGELOG-CONTROL.yaml` 주석: *"Runs on release PRs (develop -> main)"*). 그런데 이 흐름의 어느 단계에서도 PR-이슈 자동 종료(`Closes #N`)가 실제로 동작하지 않습니다. 원인은 서로 다른 두 지점에 있습니다.

**(A) feat PR — PR 템플릿에 이슈 연결 자리가 없음**

GitHub은 `Closes #N` 같은 종료 키워드를 PR의 base 브랜치가 **저장소의 기본(default) 브랜치**일 때만 실제로 파싱해서 이슈와 연결합니다(GitHub 공식 문서 "Linking a pull request to an issue": *"The special keywords ... are interpreted only when the pull request targets the repository's default branch. If the pull request targets any other branch, then these keywords are ignored, no links are created, and merging the PR has no effect on the issues."*). 이 저장소의 기본 브랜치는 `main`입니다(`gh repo view --json defaultBranchRef` 확인).

문제는 두 가지가 겹쳐 있습니다.

1. `CONTRIBUTING.md` 39~42번째 줄은 "PR은 `develop`을 향해 엽니다(이 레포는 pr-flow 브랜치 모드를 사용합니다)"라고 안내하는데, 정작 `.github/workflows/PROJECT-COMMON-ISSUE-HELPER.yaml`의 `ISSUE_HELPER_BASE_BRANCH` 환경변수는 `"main"`으로 설정되어 있습니다 — 문서와 실제 자동화 설정이 이미 서로 어긋나 있습니다.
2. 설령 개별 feat PR을 `main`을 base로 열더라도, `.github/PULL_REQUEST_TEMPLATE.md`(및 `docs/pull_request_template.md` 사본)에는 이슈 번호를 채워 넣을 자리(예: `Closes #N`)가 애초에 없습니다. 브랜치명에는 이슈 번호가 이미 포함되어 있는데(`.github/scripts/issue_helper.py`의 `create_branch_name()`이 만드는 `YYYYMMDD_#{이슈번호}_{제목}` 패턴), 이 정보를 PR 본문에 자동으로 반영해주는 장치가 없어 작성자가 매번 수동으로 적어야 하고, 실제로는 대부분 누락됩니다.

오늘(2026-08-23) PR #100(이슈 #99)에서 실측 확인했습니다: PR 본문에 `Closes #99`를 텍스트로 적었지만, base가 `develop`이었기 때문에 `gh pr view 100 --json closingIssuesReferences`가 빈 배열(`[]`)을 반환했습니다 — 텍스트만 있고 실제 GitHub 연결은 없는 상태입니다.

**(B) release PR(develop → main) — 릴리스에 포함된 이슈들이 취합되지 않음**

설령 (A)가 해결돼서 개별 feat PR이 `main`을 base로 열려 이슈가 즉시 닫히더라도, `pr-flow` 모드의 실제 배포는 `AUTO-CHANGELOG-CONTROL`이 관리하는 `develop → main` 릴리스 PR을 통해서만 이뤄집니다. `develop`에 먼저 머지됐던(base가 `develop`이라 자동 종료가 안 됐던) 이슈들은, 릴리스 PR이 `main`에 머지되는 시점에도 자동으로 닫히지 않습니다.

`.github/workflows/PROJECT-COMMON-AUTO-CHANGELOG-CONTROL.yaml`의 "Collect commits since last release" 스텝(97~109번째 줄)은 `git log origin/main..HEAD`로 "이번 릴리스에 포함된 커밋 목록"을 이미 정확히 갖고 있습니다(`commits.txt`). 이 커밋들은 이 프로젝트의 커밋 메시지 컨벤션(`{설명} : {type} : {변경설명} {이슈URL}`, `CLAUDE.md` 및 이번 세션 PR #100의 실제 커밋 예시 참고)에 따라 이슈 URL을 그대로 포함하고 있어 정규식으로 추출하기 용이한데도, 이 커밋들에서 이슈 번호를 추출해 릴리스 PR 본문에 `Closes #N` 목록으로 주입하는 로직이 어디에도 없습니다(`.github/scripts/changelog_manager.py` 전체를 확인했으나 이슈 번호 추출/링크 관련 함수 없음). 결과적으로 develop 경유 이슈들은 영구적으로 자동 종료 대상에서 빠집니다.

제안하는 해결 방법
---

- **(A) feat PR 자동 이슈 연결:** `.github/PULL_REQUEST_TEMPLATE.md`(및 `docs/pull_request_template.md`)에 "Related Issues" 섹션을 명시적으로 두고, PR이 열릴 때 브랜치명에서 이슈 번호를 파싱해(`.github/scripts/issue_helper.py`의 `extract_issue_number()`와 동일한 패턴 재사용 가능) 본문에 `Closes #N`을 자동으로 채워주는 워크플로우를 추가합니다(예: `pull_request: types: [opened]` 이벤트를 받아 `gh pr edit --body`로 append). 이 자동화는 base가 저장소의 기본 브랜치(`main`)일 때만 실제 효과가 있으므로, base 브랜치 검사를 함께 넣어야 합니다.
- **(B) release PR 자동 이슈 취합:** `PROJECT-COMMON-AUTO-CHANGELOG-CONTROL.yaml`이 이미 만드는 `commits.txt`(또는 동일한 커밋 범위)에서 이슈 URL/번호를 추출하는 서브커맨드를 `changelog_manager.py`에 추가하고(예: `extract-issue-refs`), 릴리스 PR 본문에 `Closes #N1, Closes #N2, ...` 목록을 추가하는 스텝을 "Enable automerge" 스텝 이전에 신설합니다. 자동 머지가 `main`으로 반영되는 시점에 이 목록이 PR 본문에 포함돼 있어야 GitHub이 각 이슈를 닫습니다.
- 위 두 항목 모두 `payload/workflows/common/`(사용자 배포용 템플릿 — `PROJECT-COMMON-AUTO-CHANGELOG-CONTROL.yaml`은 대응 파일 존재)과 `.github/workflows/`(이 레포 자신의 사본, 도그푸딩)에 동일하게 반영해야 합니다. 다만 PR 템플릿(`.github/PULL_REQUEST_TEMPLATE.md`)은 확인 결과 `payload/`에 대응 파일이 없는(이 레포 전용) 자산이라, (A) 관련 변경은 이 레포에만 적용하면 됩니다.
- (선택, 별도 이슈로 분리 가능) `CONTRIBUTING.md`의 "PR은 develop을 향해 엽니다" 문구와 `PROJECT-COMMON-ISSUE-HELPER.yaml`의 `ISSUE_HELPER_BASE_BRANCH: "main"` 설정이 서로 어긋나 있는 부분도 문서/설정 중 하나를 실제 관행에 맞게 정리할 필요가 있어 보입니다.

고려한 다른 방법(선택)
---

- GitHub 이슈의 "Development" 사이드바에서 매번 수동으로 PR-이슈를 연결하는 방법도 있지만, 자동 종료(close)는 여전히 안 되고 작성자가 매번 잊지 않고 눌러야 해서 근본적인 해결이 아닙니다.
- feat PR을 아예 `main`을 base로만 열도록 강제해 pr-flow(develop 경유 릴리스) 자체를 없애는 방법도 고려했지만, 이는 `AUTO-CHANGELOG-CONTROL`·`VERSION-CONTROL`·`RELEASE-PUBLISH`로 이어지는 기존 릴리스/체인지로그 자동화 설계 전체를 재검토해야 하는 더 큰 변경이라 이번 이슈 범위를 벗어나 다루지 않습니다.
