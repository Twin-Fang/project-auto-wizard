⚙️[기능추가][Go] Go 언어 프로젝트 타입 지원 추가

### 어떤 문제를 해결하고 싶으신가요?

`version.yml` 주석 기준 지원되는 `project_types`는 `spring, flutter, next, react, react-native, react-native-expo, node, python, basic`이며, `payload/workflows/`에도 `common, flutter, next, python, react, spring` 디렉토리만 있습니다. Go로 작성된 프로젝트(백엔드 서버, CLI 도구 등)는 project_type으로 감지·설치가 불가능합니다.

### 제안하는 해결 방법

Go는 다른 언어들과 달리 매니페스트 파일 안에 버전 필드가 없는 구조입니다(`go.mod`는 `module <경로>`만 가지며 자체 버전 필드가 없음 — Go 모듈 버전은 관례상 git 태그가 진실입니다). 그래서 기존 타입들과는 조금 다른 방식으로 접근해야 합니다.

- **감지**: `src/core/detect.js`가 `pyproject.toml`/`setup.py`/`requirements.txt`(24~26행 부근)로 python을, `package.json`(27행)으로 node/react류를 감지하는 것과 같은 패턴으로, `go.mod` 존재 여부로 Go를 감지하는 분기 추가.
- **버전 동기화**: `.github/scripts/version_manager.py`의 `sync_for_type()`(412~429행)을 보면 `spring`/`flutter`/`react`류/`python`/`react-native`류는 각각 매니페스트 파일을 직접 수정하지만, `basic` 타입은 아무 것도 하지 않습니다(427행, `pass`). Go는 동기화할 파일 자체가 없으므로 `basic`과 동일하게 `pass` 처리하는 것이 자연스러워 보입니다. 코드에 빌드 시점 버전을 넣고 싶다면 Go의 표준 관례인 `-ldflags "-X main.version=..."` 빌드 인젝션 방식이 있는데, 이건 version_manager.py의 "파일 동기화" 책임이 아니라 CI 워크플로우의 빌드 스텝에서 다뤄야 할 영역으로 보입니다.
- **CI 워크플로우**: `payload/workflows/python/`처럼 새 `payload/workflows/go/` 디렉토리를 만들어 `go test ./...`, `go vet`, `go build` 정도로 구성하는 방향을 제안합니다. `package.json`의 `test` 스크립트가 `test:node && test:py`로 여러 언어 툴체인을 순차 실행하는 것과 같은 패턴으로, Go 자체 툴체인만으로 동작해 project-auto-wizard의 zero-dependency 원칙과도 맞습니다.

### 고려한 다른 방법(선택)

`-ldflags` 버전 인젝션까지 `version_manager.py`가 직접 관여하는 방법도 있지만, 이건 프로젝트마다 `main` 패키지 경로·변수명이 달라 일반화하기 어려워 보입니다. 우선은 `basic`과 동일하게 버전 동기화는 생략하고, 필요하면 사용자가 CI 워크플로우에서 직접 커스터마이즈하는 쪽이 더 현실적일 것 같습니다.
