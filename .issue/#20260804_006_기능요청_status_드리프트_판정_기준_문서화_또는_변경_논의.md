🔧[기능요청][status] 대화형 설치에서 기본값이 아닌 응답만 해도 status가 항상 "드리프트"로 표시 — 의도된 설계인지 확인 및 문서화 필요

📝 현재 문제점
---

이슈 #11(전체 기능 실사용 QA)에서 발견된 H4입니다. 다른 16건과 달리 **코드 동작 자체는 확인됐지만 "버그"로 단정하지 않고 프로젝트 오너의 의도 확인을 요청**하기 위한 이슈입니다.

`--mode status`(그리고 `doctor`)의 드리프트("사용자가 수정한 파일") 판정 기준은 `src/core/wizard-env.js:98-101`의 `isUnchanged`가 담당합니다:

```js
// src/core/wizard-env.js:98-101
const virtual = substituteEnv(templateContent, { ...opts, useDefaults: true });
// 호출자가 넘긴 opts.useDefaults 값과 무관하게 항상 useDefaults: true를 강제
```

같은 파일 48행 주석에 이 의도가 명시되어 있습니다: `useDefaults   - true면 ask도 기본값 사용 (WF_USE_DEFAULTS=true, unchanged 비교의 전제)`. 즉 `isUnchanged`는 "설치본이 **기본값을 채운 템플릿**과 같은가"만 판정하도록 의도적으로 설계된 것으로 보이며, 사용자가 대화형 설치 중 실제로 어떤 응답을 했는지는 전혀 고려하지 않습니다.

**실사용 함의**: 대화형 설치(`npx project-auto-wizard`)에서 `# @wizard ask` 질문(예: `DEPLOY_PORT`)에 기본값이 아닌 값(예: `8080` 대신 `9090`)을 답하기만 해도, **설치 직후부터** `--mode status`가 해당 워크플로우 파일을 "사용자가 수정함(드리프트)"으로 보고합니다. 사용자는 파일을 전혀 편집한 적이 없는데도 status/doctor가 항상 이 파일을 "수정됨"으로 표시하게 됩니다.

재현으로 검증: `--force`(기본값 설치) 직후 status는 정상(드리프트 없음). 동일 파일의 `@wizard ask` 필드를 기본값이 아닌 값으로 수동 치환(=대화형에서 non-default 응답을 한 것과 동일한 최종 상태)한 뒤 status 재실행 → "사용자가 수정한 워크플로우 파일 (1개)"로 즉시 보고됨.

🛠️ 해결 방안 / 제안 기능
---

두 방향 중 하나(또는 조합)를 검토 요청합니다:

1. **현재 동작이 의도된 설계라면**: README(또는 `--mode status` 도움말)에 "이 드리프트 판정은 파일이 기본 템플릿과 일치하는지를 보는 것이지, 사용자가 직접 편집했는지를 추적하는 것이 아닙니다 — 대화형 설치에서 기본값이 아닌 응답을 했다면 설치 직후부터 항상 '수정됨'으로 표시됩니다"라는 내용을 명시해 오탐처럼 체감되는 혼란을 줄입니다.
2. **사용자가 실제로 편집했는지를 판정하고 싶다면**: `isUnchanged`가 비교 대상으로 삼는 "가상 기본형"을, 무조건 `useDefaults: true`가 아니라 **설치 시점에 실제로 저장된 사용자 응답값**(`version.yml`에 이미 기록되는 옵션값 등)으로 채운 템플릿과 비교하도록 변경하는 방향을 검토합니다.

🧭 구현 가이드
---

- **관련 파일**: `src/core/wizard-env.js`(`substituteEnv`, `isUnchanged`, 48행 주석), `src/commands/status.js`(드리프트 판정 호출부), `src/commands/doctor.js`(동일 판정 로직 재사용 여부 확인 필요), `README.md`(`--mode status` 설명 섹션, 152행 부근)
- 방향 ①(문서화)을 택할 경우: 코드 변경 없이 README와 `--mode status` 관련 안내 문구만 수정하면 됩니다.
- 방향 ②(판정 기준 변경)를 택할 경우: `isUnchanged`가 `useDefaults`를 강제하는 지점(101행)에서, 호출자가 실제 저장된 옵션값(`opts.values`)을 넘겼다면 그 값을 우선 사용하도록 조건 분기를 추가하는 방향이 유력해 보이나, 이 경우 3지선 충돌 판정(재설치 시 changed 여부 판단)에도 동일 함수가 쓰이므로 파급 범위를 함께 검토해야 합니다(재실행 멱등성 테스트 전체에 영향).
