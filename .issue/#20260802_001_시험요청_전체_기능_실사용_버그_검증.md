🧩 시험 대상
---

현재까지 구현이 완료된 아래 기능 전체를 대상으로 합니다.

- `npx project-auto-wizard` 대화형 설치 마법사 (`src/commands/interactive.js`)
- `--mode full` 비대화형 설치 (`src/commands/full.js`) — 단일 타입 / 멀티타입(`--type spring,react,python`) / 모노레포(`--paths`)
- `--mode version` (`src/commands/version.js`), `--mode workflows` (`src/commands/workflows.js`)
- `--mode revert` (`src/commands/revert.js`)
- `--mode status` (`src/commands/status.js`) — 설치 상태·드리프트 확인
- `--mode doctor` (`src/commands/doctor.js`) — gh CLI 인증, workflow permissions, `WORKFLOW_PAT`, merge commit 설정 점검
- `--dry-run` (`src/commands/dry-run.js`) — full/version/workflows/revert 전체 조합
- 숨김 `purge` 모드 (`src/commands/purge.js`) — 설치 이전 상태로 완전 회귀, `--delete-develop-branch` 옵션 포함
- 브랜치 모드 pr-flow / trunk-based (`src/core/branches.js`)
- 옵션 조합: `--nexus`, `--secret-backup`, `--coderabbit`, `--semver-auto` / `--no-semver-auto`, `--force`
- 프로젝트 타입 자동 감지 9종: spring, flutter, react, next, node, python, react-native, react-native-expo, basic (`src/core/detect.js`, `src/core/detect-fs.js`)
- 재실행 멱등성 및 충돌 처리(유지 / 백업 후 교체 / 참고본 추가 3지선) (`src/core/copy/*.js`, `src/core/fsutil.js`)
- 설치되는 GitHub Actions 워크플로우의 실제 동작(VERSION-CONTROL, AUTO-CHANGELOG-CONTROL, RELEASE-PUBLISH) — 로컬 CLI 산출물이 아닌 GitHub 저장소 상에서의 e2e 동작

📋 테스트 시나리오
---

1. 빈 저장소에서 `npx project-auto-wizard` 대화형 실행 — 각 질문 흐름, 기본값, 프로젝트 타입 자동 감지 결과가 실제 프로젝트 구조와 일치하는지 확인
2. `--mode full --force --type <각 9개 타입>` 개별 실행 — 타입별로 설치되는 워크플로우/스크립트가 README에 설명된 내용과 일치하는지 확인
3. `--type spring,react,python` 멀티타입 설치 — 한 저장소에 여러 타입 자산이 충돌 없이 공존하는지 확인
4. `--paths "flutter=app,react=client"` 모노레포 설치 — 마커 파일 자동 감지 및 타입별 서브폴더 경로 반영 확인
5. 설치 직후 `--mode status` 실행 — 실제 설치된 버전·타입·브랜치 모드·옵션값과 출력이 일치하는지, 사용자가 워크플로우 파일을 직접 수정한 뒤 드리프트가 정확히 감지되는지 확인
6. `--mode doctor` 실행 — `gh` 미인증, `WORKFLOW_PAT` 미등록, workflow permissions 미설정 등 각 미충족 상태에서 진단 메시지가 정확한지 확인
7. `full`/`version`/`workflows`/`revert` 각 모드에 `--dry-run`을 조합 — 실제 파일이 하나도 변경되지 않는지, 미리보기 출력이 실제 적용 결과와 일치하는지 확인
8. `--mode revert` 실행 — 설치된 워크플로우/스크립트가 정확히 원복되는지, `version.yml`은 어떻게 처리되는지 확인
9. 숨김 `purge` 모드 실행 — 설치 이전 상태로 완전히 회귀하는지, `--delete-develop-branch` 유무에 따른 로컬 브랜치 삭제 동작 차이, 작업트리 확인 실패 시 안전하게 거부되는지 확인 (최근 #6에서 구현된 안전장치 포함)
10. pr-flow / trunk-based 각 브랜치 모드로 설치 — 문서에 설명된 워크플로우 조합(pr-flow: VERSION-CONTROL+AUTO-CHANGELOG-CONTROL+RELEASE-PUBLISH 3종 / trunk-based: RELEASE-PUBLISH 단일)이 실제로 그렇게 설치되는지 확인
11. `--nexus`, `--secret-backup`, `--coderabbit`, `--semver-auto`/`--no-semver-auto` 옵션을 개별 및 조합으로 적용 — 각 옵션에 대응하는 워크플로우/설정이 정확히 반영되는지 확인
12. 동일 명령을 재실행하여 멱등성 확인 — 변경 없는 파일은 skip되는지, 사용자가 수정한 파일에 대해 유지/백업 후 교체/참고본 추가 3지선 처리가 의도대로 동작하는지 확인
13. 설치 완료 후 실제 GitHub 저장소에서 릴리스 PR을 열어 AI 릴리스 노트 작성 → CHANGELOG 갱신 → automerge → tag + Release 흐름이 문서대로 끝까지 동작하는지 e2e 확인
14. `npm test` (node --test + python unittest) 실행 결과와, 위 수동 시나리오에서 발견된 문제 중 기존 자동화 테스트로 커버되지 않는 케이스를 식별해 목록화
